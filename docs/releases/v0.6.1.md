# Axern v0.6.1

Axern v0.6.1 is the first published release of sandbox network policies. It
contains the strict and DNS-only policy feature set documented for the v0.6.0
candidate, plus a corrected source-free local readiness contract.

## Network policies

- Strict policies are fail-closed and default-deny. Domain grants require
  controlled DNS, a TTL-current destination address, and a matching HTTP
  `Host` or TLS SNI. Direct IP, alternate DNS, DoT, QUIC, ECH, missing SNI,
  HTTP `CONNECT`, and undeclared protocols remain denied.
- Explicit CIDR rules authorize only the declared IPv4 or IPv6 prefix,
  protocol, and ports. Protected local, multicast, unspecified, and metadata
  ranges cannot be opened by user policy.
- DNS deny policies return `REFUSED` for matching conventional UDP/TCP DNS
  names and CNAME chains. They intentionally do not claim strict isolation or
  block direct IP traffic, DoH, DoT, or application-owned resolvers.
- Omitting a policy preserves unrestricted v0.5.1 networking behavior. Host
  networking conflicts with policy; isolated mode becomes strict deny-all.

Python exposes `NetworkPolicy.strict`, `allow_domains`, `deny_dns`, and
`deny_all`; TypeScript exposes `strict`, `allowDomains`, `denyDns`, and
`denyAll`; Go exposes the corresponding network-policy constructors.

## Local readiness correction

`axern local up` now waits for the fresh node inventory, ready axnoded and
image manager, runtime-slot capacity, bridge networking, and the runsc
ephemeral-storage hard-limit proof required by the documented default writable
sandbox. It no longer reports ready while runtime conformance is still warming.

This preserves the default 256 MiB writable-rootfs hard limit and fail-closed
placement. It does not introduce a resolver environment-variable requirement:
local DNS upstreams continue to be derived from the effective node
configuration, and policy workloads fail closed when required upstreams are
unavailable.

## v0.6.0 candidate status

The immutable v0.6.0 candidate failed source-free local acceptance on both
linux/amd64 and linux/arm64 before any GitHub Release, PyPI, npm, final
multi-architecture image manifest, or Helm publication. Its tags remain
unchanged for auditability. v0.6.1 rebuilds and republishes every coordinated
artifact from a new commit and new tags; no v0.6.0 tag or candidate image is
moved or overwritten.

## Upgrade notes

Upgrade control-plane and node-runtime components together. Mixed v0.5.x and
v0.6.x nodes are not a supported policy-enforcement boundary. Existing
workloads without a policy retain their prior network behavior.
