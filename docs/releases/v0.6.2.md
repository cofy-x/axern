# Axern v0.6.2

Axern v0.6.2 is the first published release of sandbox network policies. It
contains the strict and DNS-only policy feature set prepared in the v0.6.0 and
v0.6.1 candidates, plus a resolver-independent OCI startup contract.

## Network policies

- Strict policies are fail-closed and default-deny. Domain grants require
  controlled DNS, a TTL-current destination address, and a matching HTTP
  `Host` or TLS SNI. Direct IP, alternate DNS, DoT, QUIC, ECH, missing SNI,
  HTTP `CONNECT`, and undeclared protocols remain denied.
- Explicit CIDR rules authorize only the declared IPv4 or IPv6 prefix,
  protocol, and ports. Protected local, multicast, unspecified, and metadata
  ranges cannot be opened by user policy.
- DNS deny policies return `REFUSED` for matching conventional UDP/TCP DNS
  names and CNAME chains. They intentionally do not claim strict isolation or
  block direct IP traffic, DoH, DoT, or application-owned resolvers.
- Omitting a policy preserves unrestricted v0.5.1 networking behavior. Host
  networking conflicts with policy; isolated mode becomes strict deny-all.

Python exposes `NetworkPolicy.strict`, `allow_domains`, `deny_dns`, and
`deny_all`; TypeScript exposes `strict`, `allowDomains`, `denyDns`, and
`denyAll`; Go exposes the corresponding network-policy constructors.

## Resolver-independent runtime startup

Axnoded no longer treats an ambient usable nameserver as a prerequisite for
OCI creation. When node-derived DNS has no usable upstream, it gives the
sandbox an owned inert `/etc/resolv.conf`. Resolver-independent workloads,
strict deny-all, CIDR-only policies, and runtime capability certification can
therefore run without DNS.

This does not weaken DNS-dependent enforcement. Explicit invalid resolver
configuration remains an error, domain-policy forwarding remains unavailable
without a verified upstream, and Axern never invents or silently falls back to
a public resolver. The former verification-only resolver override was not a
startup or release requirement and was removed when verification became fully
hermetic.

## Candidate history

The immutable v0.6.0 and v0.6.1 candidates failed source-free local acceptance
before any GitHub Release, PyPI, npm, final multi-architecture image manifest,
or Helm publication. Their tags and candidate images remain unchanged for
auditability. v0.6.2 rebuilds and publishes every coordinated artifact from new
tags; no earlier tag or candidate image is moved or overwritten.

## Upgrade notes

Upgrade control-plane and node-runtime components together. Mixed v0.5.x and
v0.6.x nodes are not a supported policy-enforcement boundary. Existing
workloads without a policy retain their prior network behavior.
